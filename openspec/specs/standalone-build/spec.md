# standalone-build Specification

## Purpose

Обеспечивает поставку утилиты в виде готового к запуску бинарного файла, который не требует на машине пользователя Python, uv или установленных пакетов, и автоматизирует получение таких файлов для Linux, Windows и macOS через GitHub Actions и GitHub Releases.

## Requirements

### Requirement: Самодостаточный бинарный файл
Система SHALL предоставлять исполняемый файл, который выполняет ту же функцию, что и консольный скрипт утилиты, и запускается на целевой операционной системе без установленного интерпретатора Python, uv и без установленных пакетов. Бинарный файл SHALL принимать те же аргументы командной строки и возвращать те же коды возврата, что и запуск из исходного окружения.

#### Scenario: Запуск без установленного Python
- **WHEN** пользователь скачивает бинарный файл для своей платформы и запускает его на машине, где Python не установлен
- **THEN** программа стартует, печатает справку по `--help` и завершается с кодом `0`

#### Scenario: Эквивалентность кодов возврата
- **WHEN** бинарный файл запускают с некорректным аргументом
- **THEN** он печатает ту же ошибку в stderr и завершается с кодом `2`

#### Scenario: Отсутствие мультимодальности при отсутствии TTY
- **WHEN** бинарный файл запускают в окружении без терминала, например в конвейере или в CI
- **THEN** он работает в текстовом режиме и печатает прогресс построчно в stdout, не запуская интерактивный интерфейс

### Requirement: Покрытые платформы
Система SHALL собирать бинарные файлы для Linux x86_64, Windows x86_64 и macOS arm64. Каждый бинарный файл SHALL собираться на раннере с архитектурой, совпадающей с целевой. Бинарный файл для macOS Intel (x86_64) системой не предоставляется.

#### Scenario: Наличие сборки под каждую заявленную платформу
- **WHEN** публикуется релиз
- **THEN** к нему приложены три бинарных файла: для Linux x86_64, Windows x86_64 и macOS arm64

#### Scenario: Отсутствие сборки под macOS Intel
- **WHEN** пользователь ищет сборку для macOS Intel
- **THEN** система сообщает, что сборки под эту архитектуру нет, и предлагает воспользоваться установкой через uv

### Requirement: Именование артефактов
Система SHALL называть каждый бинарный файл по шаблону `<имя>-<платформа>-<архитектура>` с расширением `.exe` для Windows, чтобы пользователь мог выбрать подходящий файл по одному имени.

#### Scenario: Имя файла на каждой платформе
- **WHEN** релиз содержит бинарные файлы для трёх платформ
- **THEN** они называются `ranobelib-epub-linux-x86_64`, `ranobelib-epub-macos-arm64` и `ranobelib-epub-windows-amd64.exe`

### Requirement: Проверки до сборки
Система SHALL выполнять линтер и тесты автоматически на каждом pull request и при каждом обновлении основной ветки. Релизная сборка SHALL запускаться только после того, как проверки основной ветки завершились успешно, и SHALL прерываться, если они завершились с ошибкой.

#### Scenario: Ошибка линтера блокирует сборку
- **WHEN** проверки основной ветки завершились с ошибкой линтера
- **THEN** релизная сборка не запускается

#### Scenario: Контрактные тесты не блокируют сборку
- **WHEN** тесты, требующие обращения к живому API, пропущены по умолчанию
- **THEN** это не считается ошибкой и не блокирует сборку

### Requirement: Публикация по тегу
Система SHALL создавать GitHub Release и прикреплять к нему бинарные файлы автоматически при появлении тега `v*`. Система SHALL позволять запустить сборку вручную без создания релиза.

#### Scenario: Публикация по тегу версии
- **WHEN** в репозиторий отправлен тег `v*`
- **THEN** система создаёт GitHub Release с именем тега и прикрепляет к нему готовые бинарные файлы

#### Scenario: Ручная сборка без публикации
- **WHEN** пайплайн сборки запущен вручную
- **THEN** система собирает бинарные файлы и отдаёт их как артефакты запуска, но не создаёт GitHub Release

#### Scenario: Контрольные суммы публикуются вместе с файлами
- **WHEN** релиз создан
- **THEN** к нему приложен файл с контрольными суммами SHA-256 каждого бинарного файла, позволяющий проверить целостность скачанного файла

#### Scenario: Частичный успех матрицы
- **WHEN** сборка для одной из платформ завершилась с ошибкой
- **THEN** система не создаёт релиз и сообщает, какая платформа не собрана

### Requirement: Воспроизводимость и проверка бинарного файла
Система SHALL фиксировать версию компилятора Nuitka и версию Python, использованные при сборке, и SHALL запускать получившийся бинарный файл для проверки работоспособности до того, как считать сборку успешной. Проверка SHALL использовать текстовый режим, чтобы не требовать терминала.

#### Scenario: Бинарный файл не запускается
- **WHEN** после сборки проверочный запуск бинарного файла завершается с ненулевым кодом
- **THEN** система считает сборку неуспешной и не публикует её

#### Scenario: Фиксация версий инструментов
- **WHEN** выполняется сборка
- **THEN** в журнале запуска видны версия Nuitka и версия Python, на которых она выполнена

### Requirement: Дополнительные системные зависимости не требуются
Бинарный файл SHALL работать на целевой операционной системе без установки компилятора, библиотек Pillow, текстового терминала и прочих пакетов, которые нужны для сборки утилиты из исходников.

#### Scenario: Чистая машина
- **WHEN** бинарный файл запускают на машине, где нет ни Python, ни uv, ни компилятора
- **THEN** программа работает без запроса дополнительных компонентов
