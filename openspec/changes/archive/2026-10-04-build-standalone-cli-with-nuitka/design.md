## Context

В репозитории нет каталога `.github`. Единственный способ запустить утилиту — поставить Python 3.14 и uv (`pyproject.toml` требует `requires-python = ">=3.14"`). Точка входа объявлена как `ranobelib-epub = "ranobelib_epub.cli:main"`; функция `run()` в `src/ranobelib_epub/cli/main.py` поднимает `SystemExit(main())`.

Ключевые ограничения, установленные проверкой на практике (Nuitka 4.2.2, Python 3.14.6, macOS arm64):

- Компиляция `src/ranobelib_epub/cli/main.py` как скрипта **ломает относительные импорты**. Проверено: бинарь падает с `ImportError: attempted relative import with no known parent package`, потому что модуль становится `__main__` без родительского пакета.
- `--python-flag=main` не принимается (`FATAL: Unsupported python flag 'main'`). Рабочая форма — `--python-flag=-m`, при которой Nuitka использует `<пакет>/__main__.py` как точку входа, а `__package__`/`__name__` получают значения `ranobelib_epub.cli` / `ranobelib_epub.cli.main`.
- `Nuitka` поставляет собственные конфиги пакетов для `textual`, `rich`, `PIL`, `httpx`, `anyio`, `certifi`, поэтому свой пакетный YAML не требуется.
- Полная сборка `--mode=onefile` проекта проходит без дополнительных опций: TUI на `textual` рисуется, HTTPS-запрос до `ranobelib.me` доходит (корневой сертификат `certifi/cacert.pem` подхватывается автоматически), коды возврата совпадают с исходным окружением (`--help` → 0, неизвестный аргумент → 2, книга не найдена → 1).
- Размер onefile — 22 399 456 байт (≈21,4 МиБ), распакованная папка `.dist` — 92 004 КиБ (≈89,8 МиБ), коэффициент сжатия полезной нагрузки 23,65 %, 800 C-файлов. Локальная сборка на macOS arm64 (8 CPU, 16 ГБ) заняла 550 секунд (~9,2 мин): из них ~4 мин — однопоточный Python-анализ и оптимизация, ~4-5 мин — параллельная компиляция C (447 попаданий и 353 промаха ccache), ~1 мин — упаковка onefile.
- Собранный на macOS 26 бинарь получает требование «runs on macOS 26.0 (arm64) or higher»: минимальная версия ОС наследуется от машины сборки.
- Начиная с Nuitka 4.x цель `universal` для macOS удалена, поэтому один бинарь на обе архитектуры macOS получить нельзя.
- В GitHub Actions Intel-раннеры macOS (`macos-15-intel`, `macos-26-intel`) — это larger runners, доступные только на платных планах.

## Goals / Non-Goals

**Goals:**

- Один исполняемый файл на каждую из трёх платформ, запускающийся без Python и uv.
- Сборка на подходящих под цель раннерах, без кросс-компиляции.
- Публикация по тегу `v*` в GitHub Release с однозначными именами файлов и контрольными суммами.
- Отдельные проверки (линтер, тесты) на каждом pull request и на `main`.
- Максимально широкая совместимость собранных файлов с целевыми системами.

**Non-Goals:**

- macOS Intel (x86_64) и Linux arm64 — не собираются.
- Подпись и нотарификация бинарей, публикация в Homebrew, Scoop, winget, Flatpak, AppImage.
- Установщики (NSIS, DMG, AppImage) и macOS `.app`-бандл — поставляется ровно один файл.
- Публикация пакета на PyPI и изменение способа установки через uv.
- Обфускация и защита кода отцарапанием.

## Decisions

### D1. Точка входа — `__main__.py` в пакете плюс `--python-flag=-m`

В пакет добавляется файл `src/ranobelib_epub/__main__.py`, вызывающий `run()` из `cli.main`. Сборка идёт командой `python -m nuitka --mode=onefile --python-flag=-m src/ranobelib_epub`.

**Почему.** Проверенные альтернативы не работают: компиляция `cli/main.py` рвёт относительные импорты, а отдельный тонкий скрипт-сборщик в `build/` потребовал бы либо зависимости от установленного пакета, либо дублирования точки входа. Вариант `__main__.py` — штатный механизм Nuitka, проверен на месте.

**Побочная выгода.** Появляется работающая команда `python -m ranobelib_epub` и `uv run python -m ranobelib_epub`, то же самое получают разработчики.

**Важная деталь.** При `--python-flag=-m` значение `__name__` равно `ranobelib_epub.cli.main`, а не `__main__`, поэтому защита `if __name__ == "__main__":` в `cli/main.py` не срабатывает. Вызов `run()` обязан быть явным в `__main__.py`. Это проверено на месте.

**Отвергнуто.** Правка `cli/main.py` на абсолютные импорты — не нужна и ухудшает исходники.

### D2. `--mode=onefile` на всех трёх платформах

**Почему.** Требование «скачал один файл и запустил» — ради него и затевалась сборка. Размер около 22 МБ приемлем.

**Цена.** На Windows антивирусы часто срабатывают на onefile-бинари Nuitka, а первый запуск медленнее из-за распаковки во временный каталог. Для macOS и Linux эта цена несущественна.

**План отката.** `--mode=standalone` с упаковкой результата в архив: это одна опция в скрипте сборки плюс шаг упаковки, остальной пайплайн не меняется. Переключение заложено как отдельная задача в `tasks.md`, а не как распылённая правка по трём местам.

### D3. Образы сборки фиксированы, а не `-latest`

| Цель | Раннер | Причина выбора |
| --- | --- | --- |
| Linux x86_64 | `ubuntu-22.04` | Самая низкая базовая версия glibc среди доступных образов, поэтому бинарь работает на более старых дистрибутивах. `ubuntu-latest` постепенно переезжает на 26.04, что незаметно поднимет требование к glibc. |
| Windows x86_64 | `windows-2022` | Предсказуемая база; MSVC 2022 присутствует в образе, поэтому Nuitka ничего не докачивает. |
| macOS arm64 | `macos-15` | На `macos-latest` (= macOS 26) собранный бинарь получает минимальную версию macOS 26 и не запустится на более старых системах. Более старый образ даёт более низкий порог. |

**Почему не `-latest`.** Метка `-latest` мигрирует плавно, за 1-2 месяца, и может сменить версию ОС без предупреждения в середине проекта. Для релизов нужна воспроизводимость.

**Побочный эффект macOS.** Порог минимальной версии ОС наследуется от машины сборки, поэтому задача верификации в `tasks.md` проверяет строку `runs on macOS X` в выводе Nuitka и фиксирует её как ожидаемую.

### D4. `--assume-yes-for-downloads` и согласия компилятора

На Linux и macOS Nuitka при первой сборке скачивает `ccache`. В CI это приводит к интерактивному запросу и падению задачи, поэтому везде передаётся `--assume-yes-for-downloads`. На Windows используется предустановленный MSVC, загрузка не требуется, но опция безвредна и оставляется для единообразия.

Дополнительно передаётся `--update-check=never` (в CI сеть не должна тратиться на проверку версий) и `--report=compilation-report.xml`, который загружается как артефакт при сбое: отчёт Nuitka показывает, какие модули и файлы данных попали в сборку, и резко ускоряет разбор проблем с упаковкой.

### D5. Два workflow: `ci.yml` и `release.yml`

`ci.yml` — триггеры `push` в `main` и `pull_request`; шаги `ruff check` и `pytest`. Контрактные тесты помечены маркером `contract` и по умолчанию пропускаются, поэтому `pytest` без переменных окружения их не выполняет.

`release.yml` — триггеры `push` с тегами `v*` и ручной запуск `workflow_dispatch`. Матрица из трёх платформ собирает бинарь, проверяет его запуск в текстовом режиме и выкладывает артефактом сборки. Отдельная задача `release` ждёт матрицу, скачивает артефакты, считает SHA-256 и создаёт GitHub Release.

**Почему матрица и публикация разделены.** Сборка на трёх платформах идёт параллельно, а создание релиза — один шаг, чтобы не возникло гонки за создание релиза и не пришлось бы передавать права на запись во все задачи матрицы.

**Почему проверки не дублируются в релизном пайплайне.** Тег обычно ставится на коммите, уже прошедшем проверки на `main`. Отдельная задача `needs` не даёт собрать релиз, если проверки основной ветки красные; повторный запуск тестов в каждой из трёх сборок только тратит время.

**Почему публикация через `gh release create`, а не через сторонний action.** `gh` уже есть на всех образах, поэтому не добавляется зависимость от чужого action с правами на запись в репозиторий. Права `contents: write` выдаются только задаче публикации, у остальных — `contents: read`.

**Почему `--python-flag=no_site` не передаётся явно.** Это значение по умолчанию для standalone-режима; явное указание ничего не добавляет.

### D6. Версия для метаданных берётся из `pyproject.toml`

Версия передаётся в Nuitka как `--file-version` и `--product-version`, чтобы в свойствах бинаря на Windows и в метаданных на других платформах была та же версия, что и в пакете. Источник — `pyproject.toml`, чтобы версии не расходились в двух местах.

**Компромисс.** Формат метаданных ограничен числами, поэтому версия вида `0.1.0rc1` потребует отдельной обработки; при первом появлении такой версии в схеме `--version` этот вопрос придётся решить заново. Сейчас версия простая (`0.1.0`).

### D7. Контрольные суммы и проверочный запуск

После сборки бинарь запускается с `--help`, и код возврата сверяется с ожидаемым нулём. Это ловит самый частый и самый неприятный класс ошибок упаковки — «собралось, но при запуске падает на отсутствующем модуле или файле данных». Запуск идёт в текстовом режиме: в CI нет терминала, а TUI без TTY и не должен запускаться.

Для каждого опубликованного файла считается SHA-256, и все суммы кладутся в один `checksums.txt` рядом с бинарными файлами. Это даёт пользователю способ убедиться, что файл докачался без повреждений, особенно для Windows, где onefile-файлы крупные.

Отдельный файл с версией не нужен: релиз назван по тегу, который и содержит версию, поэтому она и так видна пользователю в названии релиза.

## Risks / Trade-offs

- **Ложные срабатывания антивируса на Windows onefile** → суммы в релизе позволяют проверить файл; при подтверждении проблемы переключиться на `--mode=standalone` с архивом (D2) без переписывания пайплайна. Подпись сертификатом и `--windows-disable-console`-подобные меры вне объёма.
- **macOS Gatekeeper.** Неподписанный бинарь, скачанный из интернета, запускается с предупреждением о неизвестном разработчике. Обойти можно подписью и нотарификацией, но они требуют аккаунта разработчика Apple и платного CI для notarization. В объём не входят; в `tasks.md` добавлена проверка, что бинарь хотя бы помечается как «не помеченный», чтобы это было осознанным решением, а не сюрпризом.
- **Тихое повышение минимальной версии ОС на macOS** при смене образа → образ зафиксирован в матрице (D3), а задача верификации сверяет строку `runs on macOS X` с ожидаемой.
- **Повышение требования к glibc на Linux** при смене образа → образ зафиксирован в матрице (D3), ожидаемая базовая версия glibc проверяется отдельным шагом.
- **Падение сборки из-за отсутствующих файлов данных у новой версии зависимости.** Nuitka поставляет конфиги для `textual`, `rich`, `PIL`, `httpx`, `anyio`, но при обновлении их до версий, которые он ещё не знает, конфиг может перестать покрывать нужные ресурсы → проверочный запуск в D7 ловит это сразу на этапе сборки, а не у пользователя.
- **Долгая компиляция на Windows** (800 C-файлов на macOS) → Windows не использует `ccache`, поэтому задача будет самой долгой; это влияет на стоимость и время, но не на корректность.
- **Время выполнения задачи релизной сборки** складывается из трёх параллельных компиляций и укладывается в лимиты GitHub Actions с большим запасом.
- **Расхождение между «собирается» и «полезно»**: сборка проходит и в Python 3.14, но конкретная комбинация версий зависимостей может вести себя иначе. Локальный запуск тестов против бинаря ловит функциональные расхождения, но не покрывает платформенные различия — их проверяет сборка на всех трёх платформах.

## Migration Plan

1. Добавить `__main__.py`, `nuitka` в группу `dev`, обновить `uv.lock`.
2. Прогнать сборку локально на текущей платформе, убедиться, что `--help`, TUI и текстовый режим работают.
3. Добавить `ci.yml` и `release.yml` в ветку, выполнить релизный workflow вручную (`workflow_dispatch`) — релиза при этом не создаётся, проверяются только артефакты сборки.
4. Добавить в `README` раздел про бинарные сборки: как скачать под платформу, что macOS Intel не поддерживается, как проверить сумму.
5. Создать первый релиз: тег `v0.1.0` → собрать три платформы → опубликовать.

**Откат.** Удаление `ci.yml` и `release.yml` и отмена тега. Установка через uv при этом не затронута — она остаётся основным путём для разработчиков, бинарные файлы только дополняют её.

## Open Questions

- Стоит ли публиковать сборку для Linux arm64: официальной поддержки у Nuitka нет, но на образах GitHub есть `ubuntu-24.04-arm`. Требует отдельной проверки работоспособности Pillow под arm64; в текущий объём не входит.
